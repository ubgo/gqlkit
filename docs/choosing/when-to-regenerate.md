# When to regenerate the SDK

The generated SDK is build output derived from two inputs: the schema and your config file. With gqlkit, choosing different fields or writing a new call does not need a regeneration; the builders already cover every operation in the schema. This page lists what does need one, and how to do it so nothing stale is left behind.

## Before you start

Have the regeneration as one command (a script or a Taskfile task) so it is run the same way every time. [`example-cli/generate-go.sh`](../../example-cli/generate-go.sh) and [`example-cli/generate-ts.sh`](../../example-cli/generate-ts.sh) are complete versions; the [keep-in-sync recipe](../recipes.md#keep-the-sdk-in-sync-as-the-schema-changes) shows a Taskfile.

## Decision table

| What changed | Regenerate? | Why |
| --- | --- | --- |
| You select different fields, add a call, change arguments | No | The builders already expose every field and argument in the schema. |
| The server added or removed an operation, type, field, argument or enum value | Yes | The SDK only knows the schema it was generated from. |
| You changed `config.jsonc` (a scalar binding) | Yes | Bindings are compiled into `scalars/`. |
| You changed the `gqlkit-sdl` filter flags | Yes, after re-fetching | The filtered schema is a different input. |
| You upgraded the `gqlkit` binary | Yes | Templates change between versions; check the [gqlkit changelog](../../gqlkit/CHANGELOG.md). |
| You upgraded `gqlkit-ts` | Usually not | The TS SDK imports the runtime; regenerate if its changelog says so ([gqlkit-ts changelog](../../gqlkit-ts/CHANGELOG.md)). |
| You moved the Go SDK to another directory or module | Yes | The import path is written into every Go file. |

## Step 1: Generate with --prune

By default the generators overwrite the files they write but never delete anything. When an operation disappears from the schema, its old builder file stays and usually stops compiling against the new types. `--prune` removes those leftovers after a successful run: it deletes files in the output directory that carry the `Code generated by gqlkit. DO NOT EDIT.` banner but were not written by this run. Files without the banner (your own helpers) are never touched. Preview first with `--dry-run`, which lists what would go and deletes nothing:

```sh
gqlkit generate -s schema.graphql -o ./sdk -m "$(go list -m)/sdk" -c config.jsonc --prune --dry-run
gqlkit generate -s schema.graphql -o ./sdk -m "$(go list -m)/sdk" -c config.jsonc --prune
```

```sh
gqlkit generate-ts -s schema.graphql -o ./src/sdk -c config.jsonc --prune
```

`--dry-run` without `--prune` is an error, so a dry run can never silently do nothing. From Go code, set `Prune` and `PruneDryRun` on `clientgen.Config` / `clientgents.Config`. The older approach, `rm -rf sdk` before generating, still works, but only for a directory that holds nothing except generated code.

## Step 2: Build right after

Run `go build ./...` (Go) or `tsc --noEmit` (TypeScript) as part of the same command. A schema change that removed a field you use fails here, at compile time, which is the main reason to keep the SDK typed.

## Step 3: Decide what to commit

Commit the schema (`schema.graphql`) so every schema change is a reviewable diff. For the SDK itself, either commit it (no generator needed to build the app; diffs show API changes) or generate it in your build (no generated code in review). Both work; pick one and make CI check it.

## Try it

`example-cli/test.sh` regenerates on every run (each script removes its output directory first) and builds the result:

```sh
./example-cli/test.sh
```

## Pitfalls

- **Stale files.** Covered above; the symptom is a build error in a generated file for an operation that no longer exists. Use `--prune`.
- **A refetch that silently changed the scope.** Changing filter flags and forgetting `--remove-unused` keeps every type; changing them so every mutation is removed drops the `Mutation` type with only a stderr note (see [Filter a schema](../cli/filter-schema.md#pitfalls)).
- **Regenerating from a different directory.** Without `-m`, the Go import path comes from the nearest `go.mod` plus the output directory, and `-o ./sdk` means a different directory when run from somewhere else, so every import changes. Pass `-m` in scripts.
- **Two languages drifting.** If you generate Go and TypeScript from one schema, regenerate both in the same command.
